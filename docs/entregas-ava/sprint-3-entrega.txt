PARTE 1 — INFRAESTRUTURA DO BACKEND                        

1. BANCO DE DADOS — PRISMA + SUPABASE (POSTGRESQL)

   O banco de dados foi modelado com Prisma ORM e hospedado no Supabase
   (PostgreSQL gerenciado na nuvem, região São Paulo — aws-sa-east-1).

   Entidades do schema (apps/api/prisma/schema.prisma):
   - User:        id, name, email, cpf, phone, passwordHash, role, status
   - Vehicle:     id, plate, brand, model, year, color, status
   - Driver:      id, name, cpf, cnh, cnhExpiry, phone, status
   - Expense:     id, vehicleId, type, amount, date, description
   - Maintenance: id, vehicleId, type, status, scheduledDate, completedDate
   - Document:    id, vehicleId?, driverId?, type, expiryDate, alertSent

   Relacionamentos:
   - Vehicle 1:N Expense
   - Vehicle 1:N Maintenance
   - Vehicle 1:N Document
   - Driver 1:N Document
   - Vehicle N:M Driver (tabela _VehicleDrivers)

   Seed inicial (apps/api/prisma/seed.ts):
   - Cria o usuário administrador padrão com senha hasheada
   - Cria um veículo e um motorista de exemplo para testes

   Migrations aplicadas:
   - init:                    criação de todas as tabelas
   - add_user_status:         adição do campo status ao usuário
   - remove_auth0_add_custom_auth: substituição de campos Auth0 por
                              passwordHash e status de aprovação

2. AUTENTICAÇÃO PRÓPRIA — JWT + BCRYPT + SUPABASE

   O sistema de autenticação foi desenvolvido inteiramente do zero,
   sem dependência de serviços de identidade externos.

   Tecnologias:
   - bcryptjs: hash e verificação de senhas
   - jose:     assinatura e validação de tokens JWT com JWT_SECRET

   Endpoints de autenticação:
   - POST /auth/register  — solicita acesso ao sistema (status: PENDING_APPROVAL)
   - POST /auth/login     — valida credenciais e retorna token JWT

   Fluxo completo:
   a) Novo usuário se registra → status PENDING_APPROVAL
   b) Administrador aprova o usuário → status ACTIVE
   c) Usuário faz login → backend valida senha com bcrypt e assina JWT
   d) Token é enviado em todas as requisições: Authorization: Bearer <token>
   e) Middleware extrai userId do token e busca o User no banco
   f) Middleware RBAC verifica o role antes de liberar cada rota

   Arquivos:
   - apps/api/src/services/auth.service.ts
   - apps/api/src/controllers/auth.controller.ts
   - apps/api/src/routes/auth.routes.ts
   - apps/api/src/lib/verify-token.ts

3. MIDDLEWARES DO BACKEND

   authenticate.ts
   - Valida o token JWT em cada requisição protegida
   - Extrai o userId e busca o User no banco
   - Rejeita tokens inválidos ou usuários bloqueados (401/403)

   authorize.ts
   - Controle de acesso baseado em perfil (RBAC)
   - Roles: ADMIN, MANAGER, OPERATOR
   - Bloqueia requisições de roles sem permissão (403)

   validate.ts
   - Valida o body das requisições com schemas Zod
   - Remove campos extras não declarados no schema
   - Retorna erros de validação formatados (400)

   error-handler.ts
   - Captura todos os erros da aplicação
   - Formata respostas de erro consistentes (AppError)

4. MÓDULO DE USUÁRIOS — BACKEND

   Endpoints:
   - GET  /users      — lista todos os usuários (ADMIN)
   - GET  /users/me   — retorna dados do usuário autenticado
   - PUT  /users/:id/role    — altera o role de um usuário (ADMIN)
   - PUT  /users/:id/status  — aprova ou bloqueia um usuário (ADMIN)

   Regra de proteção:
   - A conta administradora principal não pode ter seu role ou status
     alterados, evitando bloqueio acidental do sistema.

   Arquivos:
   - apps/api/src/repositories/user.repository.ts
   - apps/api/src/services/user.service.ts
   - apps/api/src/controllers/user.controller.ts
   - apps/api/src/routes/user.routes.ts


  PARTE 2 — MÓDULOS DE NEGÓCIO                               

5. BACKEND — API REST DE DESPESAS

   Registra gastos operacionais associados a veículos.

   Endpoints:
   - GET    /expenses        — listagem com filtros por veículo, tipo e período
   - GET    /expenses/:id    — detalhes de uma despesa
   - POST   /expenses        — registro de nova despesa
   - PUT    /expenses/:id    — edição
   - DELETE /expenses/:id    — exclusão (ADMIN e MANAGER)

   Tipos de despesa: FUEL | MAINTENANCE | FINE | IPVA | INSURANCE | OTHER

   Testes unitários: 9 testes (Vitest, TDD)
   Arquivos:
   - apps/api/src/repositories/expense.repository.ts
   - apps/api/src/services/expense.service.ts
   - apps/api/src/controllers/expense.controller.ts
   - apps/api/src/routes/expense.routes.ts

6. BACKEND — API REST DE MANUTENÇÕES

   Registra revisões e reparos dos veículos.

   Endpoints:
   - GET    /maintenances        — listagem com filtros por veículo, tipo, status
   - GET    /maintenances/:id    — detalhes
   - POST   /maintenances        — registro
   - PUT    /maintenances/:id    — edição / atualização de status
   - DELETE /maintenances/:id    — exclusão (ADMIN e MANAGER)

   Tipos: PREVENTIVE | CORRECTIVE
   Status: SCHEDULED | DONE | OVERDUE

   Regra de negócio: ao marcar uma manutenção como DONE, o campo
   completedDate é preenchido automaticamente com a data atual.

   Testes unitários: 10 testes (Vitest, TDD)
   Arquivos:
   - apps/api/src/repositories/maintenance.repository.ts
   - apps/api/src/services/maintenance.service.ts
   - apps/api/src/controllers/maintenance.controller.ts
   - apps/api/src/routes/maintenance.routes.ts

7. BACKEND — API REST DE DOCUMENTOS

   Controla documentos obrigatórios de veículos e motoristas
   (CRLV, CNH, seguro, etc.) com cálculo automático de status de vencimento.

   Endpoints:
   - GET    /documents              — listagem com status computado
                                     (VALID / EXPIRING_SOON / EXPIRED)
   - GET    /documents/:id          — detalhes
   - POST   /documents              — cadastro de documento
   - PUT    /documents/:id          — edição
   - DELETE /documents/:id          — exclusão (ADMIN e MANAGER)
   - GET    /documents/alerts/count — contagem de documentos vencidos/próximos

   Regra de negócio:
   - Documentos com vencimento nos próximos 30 dias → status EXPIRING_SOON
   - Documentos com vencimento passado → status EXPIRED
   - Status VALID para os demais

   Testes unitários: 15 testes (Vitest, TDD)
   Arquivos:
   - apps/api/src/repositories/document.repository.ts
   - apps/api/src/services/document.service.ts
   - apps/api/src/controllers/document.controller.ts
   - apps/api/src/routes/document.routes.ts

8. BACKEND — JOB DE ALERTAS DE VENCIMENTO (CRON)

   Um job agendado verifica diariamente os documentos próximos do
   vencimento e marca o campo alertSent para evitar alertas duplicados.

   Tecnologia: node-cron
   Execução: diariamente à meia-noite
   Comportamento: idempotente — documentos já marcados com alertSent=true
   não são reprocessados.

   Arquivo: apps/api/src/alertCron.ts

9. BACKEND — DASHBOARD DE INDICADORES FINANCEIROS

   Endpoint que agrega dados reais do banco para o painel gerencial.

   - GET /dashboard/indicators — retorna:
     * Total de despesas do mês atual
     * Total de despesas do mês anterior
     * Despesas agrupadas por mês (últimos 6 meses)
     * Despesas agrupadas por tipo

   Testes unitários: 2 testes (Vitest, TDD)
   Arquivos:
   - apps/api/src/repositories/dashboard.repository.ts
   - apps/api/src/services/dashboard.service.ts
   - apps/api/src/controllers/dashboard.controller.ts

DECISÕES TÉCNICAS
-----------------
- Autenticação própria (JWT + bcrypt) foi escolhida para independência
  de serviços externos e controle total sobre o fluxo de aprovação.
- O status PENDING_APPROVAL permite ao administrador revisar e aprovar
  novos usuários antes que eles acessem o sistema.
- O banco foi migrado para o Supabase (PostgreSQL gerenciado) para
  garantir disponibilidade sem necessidade de infraestrutura local.
- O Prisma é a única interface de acesso ao banco; nenhuma consulta SQL
  manual é executada no código.
- O cron job de alertas é idempotente: pode ser executado múltiplas vezes
  sem gerar alertas duplicados.
